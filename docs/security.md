# Security rules

These are requirements, not preferences. Each one closes a hole that is cheap
to create and expensive to discover in production.

## No *user* passwords exist

User authentication is OAuth2 / OIDC only — Google for the first test. The API
stores no user credentials and owns no reset or recovery flow. That whole class
of vulnerability is absent because the feature is absent.

**One correction to an earlier version of this document:** the API does now hash
one thing — the **room password** that gates private rooms, alongside the join
code. That is a shared secret for an object, not a credential for a person: it
cannot be credential-stuffed, its compromise exposes one room rather than an
account, and the owner changes it while signed in instead of through email. User
authentication remains passwordless. The rules for it — Argon2id, generated by
default, single generic error, and the DoS interaction with the co-located SFU —
are in [`room-access.md`](room-access.md).

The OAuth-specific rules — mandatory `state`, PKCE, exact-match redirect URIs,
full ID-token validation, verified-email account linking, and the
`SameSite=Lax` requirement on the state cookie — live in
[`authentication.md`](authentication.md). They are requirements, not
suggestions; social login moves the risk from credential storage to flow
correctness rather than eliminating it.

## Secrets never reach the client

- The **LiveKit API secret**, the **OAuth2 client secret** and **database
  credentials** exist only in the backend's environment. They are never
  bundled, never served, never returned by an endpoint.
- The browser never receives a provider access token, refresh token or
  authorization code. The backend is a confidential client; the SPA holds only
  an HttpOnly session cookie.

  **Correction, 29 October 2026:** that cookie is signed, not encrypted, so it
  is not literally opaque as earlier versions of this document said — its own
  holder can read the display name, email and plan inside it. Nobody else can,
  and nobody can alter it without the signing secret. The reason it is signed
  rather than stored server-side is that a guest session then needs no row at
  all, which is what [`authentication.md`](authentication.md) describes. Two
  consequences follow and are not yet addressed: signing out clears the cookie
  rather than revoking the session, so a stolen cookie works until it expires,
  and the per-account concurrent-session cap below needs server-side session
  records that do not exist.
- The browser receives only short-lived, narrowly-scoped LiveKit tokens.
- A build that can reach `LIVEKIT_API_SECRET` from frontend code is a broken
  build, not a configuration choice.

## Never trust a client-supplied plan or quality flag

Resolution caps, FPS caps, the subscription limit and room capacity are derived
**server-side** from the authenticated user's plan and the room's state at the
moment the token is minted.

A request that says "I am premium, give me 1080p" is treated as a request for
whatever that user's plan actually permits. The client may *ask* for a quality;
it may never *assert* an entitlement.

## Private rooms are checked before a token exists

The access check runs **before** `POST /v1/rooms/{code}/token` returns anything.
There is no path that mints a token and then checks whether the caller was
allowed in. Ordering matters: a token issued to an unauthorised caller is
already a breach, even if a later check would have rejected them.

A private room admits on **either** of two proofs:

- a valid **invite** for the caller's identity — requires sign-in
- a verified **join code + room password** — does not

Invite tokens are stored hashed, carry an expiry, and are single-use unless the
room owner explicitly created a reusable link.

**Never confirm that a code exists.** A wrong code, a right code with a wrong
password, and a nonexistent room return one identical error, with no room title,
description or participant count, and with indistinguishable timing. A two-step
"code valid, now enter the password" flow is an enumeration oracle. Details in
[`room-access.md`](room-access.md).

## User-generated room text is untrusted

`title` and `description` are written by users and rendered to other people.
Store and emit them as text, never as HTML. Normalise to NFC, strip control
characters, and reject zero-width and bidirectional override characters —
anywhere public rooms are listed, those are the usual tools for homoglyph and
RTL display abuse. A private room's title and description are not disclosed at
all until code and password verify.

## Tokens are short-lived and minimally scoped

Every LiveKit token carries:

- exactly one room name
- the minimum grants for that role — `canPublish` for any admitted participant,
  `canSubscribe` with the plan's subscription cap applied,
  `canPublishData` only if the feature needs it
- a short TTL, long enough to join and reconnect, not to be shared around
- an identity that maps back to a `sessions` row

The subscription cap is the grant that matters here. Publishing is unrestricted
by design, so the token's job is not to decide *who may share* — it is to bound
*how much each participant receives.* A viewer who ends up subscribed to all ten
streams in a room is not a quality bug, it is a cost incident: it costs as much
as nine well-behaved ones.

**Correction, 29 October 2026:** that bound is not expressible in the token.
`canSubscribe` is a boolean, and LiveKit offers no numeric per-viewer limit
anywhere — not in the grant, not in `ParticipantPermission`, not in the room
service API. The cap of one is enforced by the client connecting with
auto-subscribe disabled and the API driving every subscription through
`POST /v1/rooms/{code}/subscription`; see
[`plans-and-limits.md`](plans-and-limits.md). The token still grants
`canSubscribe`, because without it a participant could not watch anything at
all.

Reconnection mints a fresh token through the same checks rather than reusing
the old one.

## Rate limiting and abuse

- **OAuth `/start` and `/callback`**, **room creation**, **token issuance** and
  **`POST /v1/rooms/join`** are all rate-limited per user and per IP.
- **The join endpoint needs the strictest limit, applied before any hashing.**
  It is both a brute-force target and, because Argon2id is deliberately
  expensive, a CPU-exhaustion vector against a VM that is also forwarding media.
  Rate-limit per code **and per IP**, with the backoff keyed on both, and cap
  concurrent verifications. The flat budget is keyed on the code alone, so
  rotating source addresses does not raise the ceiling on hashing; the
  escalating lockout is keyed on the code and the caller, so one guesser
  cannot lock a room against the people who know its password. This matches
  [`room-access.md`](room-access.md), which said "per code, per IP" all along;
  this line was the looser summary of the two. Token issuance is the more important of the two: it is the endpoint that
  costs money, because each token admits a participant who consumes a stream for
  an unlimited session.
- **Unlimited session length removes the natural brake on abuse.** With no time
  limit, a single admitted participant can hold a subscription indefinitely, so
  idle-room reaping and per-account concurrent-session caps do the work that a
  session timeout would otherwise do. Worth building in Phase 2 rather than
  after the first abandoned room runs for a week. **Idle-room reaping is now
  built**, by the SFU rather than by us: each room is created with an
  empty-timeout, so LiveKit closes it once the last participant leaves and it
  stays empty. The per-account concurrent-session cap is still blocked on the
  server-side session records noted above.
- Room owners get moderation controls: remove a participant, revoke an
  individual's `canPublish` grant, lock the room. Because publishing is
  uncapped, per-participant revocation is the *only* way to stop an abusive
  share — there is no slot limit that incidentally contains it.
- Anyone in a room can file an abuse report. Public rooms are the exposed
  surface here — they are joinable by definition.

## Transport and operations

- HTTPS and WSS everywhere. No mixed-content path, no plaintext signalling.
- Firewall rules limiting inbound to the ports actually in use. A self-hosted
  SFU needs its UDP range reachable, which is a wider surface than an API-only
  host — see [`livekit-hosting.md`](livekit-hosting.md).
- Database backups, with a restore that has actually been tested.
- Monitoring on CPU, memory, packet loss, bandwidth and latency. For a
  self-hosted SFU these are not vanity metrics; they are the early warning that
  the media server is starving the API.
