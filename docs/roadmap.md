# Implementation plan

Phases are ordered so each produces something testable, and so the riskiest
unknown — how many concurrent rooms the Oracle VM carries with all participants
publishing — is measured before much is built on top of it.

## Phase 0 — Confirm the ground truth

Before writing deployment code.

- **Confirm the VM's region.** It must be `sa-saopaulo-1` or `sa-vinhedo-1`.
  A US-region instance costs Brazilian users ~110–160 ms RTT; migrating is a
  Phase 0 task, not a later optimisation. This is the one remaining blocker from
  [`open-questions.md`](open-questions.md).
- Check block storage and outbound-transfer charges on the account. Free
  compute does not imply free volumes or egress.
- Confirm `arm64` builds for the Go toolchain, PostgreSQL and the LiveKit
  server image.
- Register the Google OAuth2 client and the exact callback URIs for local
  development and the deployed host. Exact-match only, no wildcards.
- Recheck LiveKit Cloud's current rates, so the self-host decision rests on
  today's numbers even though the decision is already made.

The instance shape and Always Free status are confirmed; see decision 1.

## Phase 1 — Walking skeleton

- Go API with health check, configuration loading, structured logging.
- PostgreSQL with the schema from [`architecture.md`](architecture.md).
- Self-hosted LiveKit in a Brazil region, TLS and WSS terminated, UDP range
  open.
- `POST /v1/rooms/{code}/token` minting a correct short-lived token for a
  hardcoded test room.
- Frontend joins and publishes one screen.

Done when two browsers see each other's screens over the deployed stack.

## Phase 2 — The security boundary

- **Google OAuth2 login** via the BFF flow: `/start` with state + PKCE,
  `/callback` with full ID-token validation, HttpOnly session cookie. One
  provider enabled, behind the multi-provider `Provider` interface and
  `identities` schema from [`authentication.md`](authentication.md).
- Guest sessions for anonymous public-room access.
- Room creation with **title and description**, public and private visibility.
- **Join codes** (10-char Crockford base32, rotatable) and **private-room
  passwords** (Argon2id, generated by default), per
  [`room-access.md`](room-access.md).
- `POST /v1/rooms/join` verifying code and password **together**, with one
  generic error and indistinguishable timing.
- Invite issue and redemption, hashed and expiring.
- The full ordered check in the token handler: visibility → (invite **or**
  code+password) → capacity → plan.
- Rate limits on OAuth endpoints, room creation and token issuance.
- Idle-room reaping and per-account concurrent-session caps — the brake that
  unlimited session length removes.

Done when every rule in [`security.md`](security.md) and
[`authentication.md`](authentication.md) has a test that fails if the rule is
removed. Worth being strict about — these are the checks that are easiest to
reorder by accident in a later refactor. Specifically: a test that the OAuth
callback rejects a mismatched `state`; one that it rejects an ID token with the
wrong `aud`; and one asserting that a nonexistent code, a wrong password and a
valid pair are **indistinguishable** in response body for the two failures.

## Phase 3 — Subscription cap and dynacast

The phase that makes the cost model real. Both items here are load-bearing.

- **Server-side subscription cap of 1**, via LiveKit participant permissions.
  Frontend state alone is not enforcement.
- Stream switching that unsubscribes the old track **before** subscribing to the
  new one.
- **Dynacast enabled**, so published tracks with no subscribers are paused.
- `canPublish` granted to every admitted participant — no slot accounting.
- Immediate participant removal on disconnect, driven by the
  `participant_left` webhook.
- Quality caps derived server-side from the plan; server-side simulcast layer
  config.
- Optional system audio with graceful video-only fallback.
- Screen picker that does not hold live subscriptions to every stream — see the
  thumbnail trap in [`media-bandwidth.md`](media-bandwidth.md).

Done when a 10-person room with all 10 publishing measures ~20 Mbps downstream,
not ~180 Mbps, and ingest drops measurably when viewers converge on a few
screens.

## Phase 4 — Measurement

- LiveKit webhooks → `sessions` records.
- Per-session participant-minutes, downstream bytes and **ingress bytes**.
- `watched_seconds` accumulating per participant across reconnects — the
  accounting the future ad break depends on.
- Count of published tracks with zero subscribers, as a dynacast-effectiveness
  metric.
- A report answering: participant-minutes per plan, downstream and ingest GB per
  plan, peak concurrent publishers, and how often viewers switch streams.

Without this the pilot produces a working product and no information. It is not
a nice-to-have; Phase 5's capacity number and the premium price both depend on
it.

## Phase 5 — Load test and capacity

This phase produces the number that prices premium.

- Load-test the decided model: 10 participants, **all 10 publishing** at 720p30,
  one subscription each, dynacast on, sustained.
- Scale concurrent rooms until CPU or packet loss degrades. That ceiling is
  **C**, the concurrent-rooms-per-VM figure.
- Watch CPU, packet loss, memory, bandwidth and latency throughout.
- Feed `C` into the premium pricing calculation in
  [`open-questions.md`](open-questions.md).
- Decide whether to split the SFU onto its own host.

## Phase 6 — Operational hardening

- Backups with a tested restore.
- Monitoring and alerting on the Phase 5 metrics, with an alert at ~70%
  sustained CPU.
- Moderation tools for room owners; abuse reporting.
- TURN for restrictive networks, if the pilot shows connection failures.

## Later — ads

Deferred, with hooks in place from Phases 3–4. The enforceable design: at the
hourly checkpoint the API revokes `canSubscribe` through LiveKit's
participant-permissions API, the client plays the ad and confirms, the API
restores the permission. Media stops because the server stopped it.
